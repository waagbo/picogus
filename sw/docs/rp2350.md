# RP2350 (Raspberry Pi Pico 2 / Pico 2 W) support

PicoGUS firmware can be built for the RP2350 as well as the RP2040. RP2040
builds are unaffected: the RP2350 port leaves the RP2040 release images (the
multifw bundle with its bootloader and per-mode images, and the NE2000
firmware) byte-identical, apart from the firmware-flashing safety checks
described below.

**Status: builds and passes static checks, not yet tested on hardware.** See
[Hardware test checklist](#hardware-test-checklist).

## Supported hardware

| Board | RP2040 firmware | RP2350 firmware |
|---|---|---|
| PicoGUS 1.x / Femto with a Raspberry Pi Pico | `picogus.uf2` | – |
| PicoGUS 1.x / Femto with a Pico W (NE2000) | `pg-ne2k.uf2` | – |
| PicoGUS 1.x / Femto with a Raspberry Pi Pico 2 | – | `picogus-rp2350.uf2` |
| PicoGUS 1.x / Femto with a Pico 2 W (NE2000) | – | `pg-ne2k-rp2350.uf2` |
| PicoGUS 2.0 (chip-down RP2040) | `picogus.uf2` | – |

Only the 30-GPIO RP2350A is supported, which is what Pico-footprint modules
like the Pico 2 use. RP2350B boards (such as the Pimoroni Pico Plus 2) would
need board detection ported: it reads GPIO29 through the ADC, and the RP2350B
ADC inputs are GPIO40–47. The build stops with an error for RP2350B.

The two chips' firmwares are not interchangeable. The USB bootloaders only
accept UF2 files for their own chip, and `pgusinit /flash` is refused by
firmware from this version on when the file is for the other chip. Older
firmware does not have that check, so don't `/flash` an `-rp2350` file to an
RP2040 card running an older release.

## Building

Needs the same tools as before: pico-sdk 2.1.1, pico-extras `sdk-2.1.1` and
arm-none-eabi-gcc 14.2, with `PICO_SDK_PATH` and `PICO_EXTRAS_PATH` set.

The harness builds any mix of variants for one or both chips:

```sh
sw/scripts/build_variants.sh                  # multifw + ne2k, RP2040 and RP2350
sw/scripts/build_variants.sh -p rp2350 all    # every variant, RP2350 only
sw/scripts/build_variants.sh --list           # variants and their PROJECT_TYPEs
```

UF2 files are collected in `binaries/` (RP2350 ones with an `-rp2350` suffix),
and each build gets its own directory under `build/<chip>/<variant>`. CI runs
the same script for both chips.

A single build works as before, with `-DPICO_PLATFORM=rp2350` added:

```sh
cmake -S sw -B build-rp2350 -DPICO_PLATFORM=rp2350 -DPROJECT_TYPE=MULTIFW
cmake --build build-rp2350
```

The board then defaults to `pico2_fast` (`pico2w_fast` for NE2K). Passing an
RP2350 board with `-DPICO_BOARD` also works. RISC-V (`rp2350-riscv`) is not
supported, as the OPL emulator and the multifw bootloader contain Arm code.

## What is different on RP2350

**GPIO.** RP2350 pads come out of reset with the input buffer disabled and the
pad isolation latch set. `gpio_set_function()` clears both, but the ISA bus
pins that are only ever sampled by PIO (AD0–AD9, IOR, IOW, DACK, TC) never go
through it and would read as 0. They are enabled explicitly
(`platform_gpio_enable_input()` in `system/platform.h`).

**Overclock** (`system/overclock.h`). Still 370 MHz, with the core voltage at
1.30 V (1.25 V on RP2040): the RP2350 is rated for 150 MHz at 1.10 V, and
1.30 V is the highest setting that doesn't need `vreg_disable_voltage_limit()`.
Override with `PICOGUS_VREG_VOLTAGE`.

**Flash clock.** On RP2040, boot2 sets the flash clock divider
(`PICO_FLASH_SPI_CLKDIV 4`). The RP2350 has no boot2; its bootrom leaves the
flash interface (QMI) in the fastest mode it found to work at boot, normally
with divider 3, which is 50 MHz at the stock 150 MHz but 123 MHz at 370 MHz.
`overclock_370mhz()` therefore sets the divider to 6 (61.7 MHz) with a 2
half-cycle read delay before raising the clock, keeping the bootrom's read
mode. Flash writes put the bootrom's divider back, which is why this happens
on every call (the firmware already calls it after each settings save).
Override with `PICOGUS_FLASH_QMI_CLKDIV` / `PICOGUS_FLASH_QMI_RXDELAY`. The
ROM's erase and program routines use their own divider (12), so flash writes
are within spec at any clock.

**Multifw.** RP2350 images have no 256-byte boot2 in front of the vector
table, so the bootloader jumps to the start of the firmware slot (and sets
VTOR through `M33_VTOR_OFFSET`). Each chip has its own copy-to-RAM linker
script under `multifw/<chip>/`, and `uf2create` writes the RP2350 Arm-Secure
UF2 family ID. The SDK's runtime init resets the bootrom state and boot locks
before re-enabling bootrom locking, so starting a second image after the
bootloader works as on RP2040.

**UF2 files and erratum RP2350-E10.** The RP2350 board headers deliberately
leave `PICO_RP2350_A2_SUPPORTED` unset, so picotool doesn't add the E10
workaround block to UF2s. E10 only affects flash with a partition table,
which PicoGUS doesn't use, while the workaround block erases the last flash
sector on A2 chips (where PicoGUS keeps its settings) and is a separate
"file" inside the UF2 that `pgusinit /flash` can't handle.

**Reboot after `pgusinit /flash`** uses the watchdog on RP2350; Arm
`SYSRESETREQ` is only a processor warm reset there.

**Resampler.** The OPL resampler's Cortex-M0+ inline assembly can't be
register-allocated for Cortex-M33, so RP2350 uses an equivalent C loop (same
wrapping 32-bit arithmetic).

**NE2000.** The CYW43 SPI clock divider is 4 on RP2350 (46.25 MHz, within the
CYW43439's 50 MHz limit); RP2040 keeps its divider of 3 (61.7 MHz).

**Settings** are still kept in the last flash sector, which is at 4 MB − 4 KB
on the Pico 2's 4 MB flash.

**Firmware string.** RP2350 builds append ` (RP2350)` to the version shown by
pgusinit.

### Errata reviewed

- RP2350-E1 (interpolator shifts are rotates): every interpolator lane used
  masks off the rotated-in bits (emu8950 slot renderer, SB linear
  interpolation, clamp), so results match RP2040.
- RP2350-E2 (SIO spinlock aliasing): the SDK uses software spinlocks on
  RP2350; PicoGUS code only uses the SDK spinlock API.
- RP2350-E9 (A2 only, input pad leakage): bus inputs are driven by the
  board's transceivers; DACK and TC keep the same pull-downs as on RP2040.
- RP2350-E12 (USB status synchronisation): needs clk_sys ≥ 1.1 × clk_usb,
  which holds at 370 MHz and at the 240/125 MHz used around flash writes.
- RP2350-E27 (bus priority wiring): PicoGUS doesn't change bus priorities.

## Hardware test checklist

None of this has run on an RP2350 yet. Things to check on a PicoGUS 1.x board
with a Pico 2 (and a Pico 2 W for NE2000):

1. Boot from a drag-and-drop `picogus-rp2350.uf2`; pgusinit detects the card
   and shows `(RP2350)` in the firmware string.
2. Every mode, and switching between them with `/mode` (exercises the multifw
   bootloader jump and watchdog reboot).
3. GUS mode: PSRAM detection (the firmware tries both SPI timing strategies),
   long demos with DMA.
4. SB mode: 8/16-bit, auto-init and high-speed DMA, OPL3, CD-ROM images from
   USB, CD audio, joystick, MPU-401 MIDI out.
5. AdLib, MPU, PSG (Tandy/CMS) and USB modes, including the USB mouse.
6. `pgusinit /save` followed by a reboot (flash write at runtime, then the
   flash divider being restored) and a power cycle.
7. `pgusinit /flash` with a matching file, with an RP2040 file (must be
   refused without harming the card), and with a truncated file.
8. NE2000 on a Pico 2 W: connect, `/wifistatus`, file transfers.
9. Long runs at 370 MHz / 1.30 V, ideally in a warm case. If flash reads
   misbehave, raise `PICOGUS_FLASH_QMI_CLKDIV`; if the core is unstable, the
   voltage and `RP2_CLOCK_SPEED` are the knobs.
