# Sound Blaster and NE2000 at the same time on RP2350

Investigation into running the SB16 emulation (with OPL3, MPU-401, CD-ROM and
USB) and the NE2000/WiFi emulation together on one card with a Raspberry Pi
Pico 2 W. The experimental `SB_NE2K` firmware described below builds and links;
nothing here has been tested on hardware.

## Summary

- **The RP2350 has the resources.** The combined firmware links with 191 KB of
  static RAM and leaves 321 KB of heap, of which the NE2000 packet buffer takes
  33 KB. PIO, DMA channels, timer alarms and pins all fit with room to spare,
  and the WiFi work can be scheduled on core 1 without starving the audio.
- **The card is the blocker.** Every PicoGUS board has a single ISA IRQ
  output. SB digital audio and an NE2000 packet driver each need their own
  interrupt, and DOS drivers can't share an edge-triggered ISA IRQ. Using both
  at the same time (for example an IPX network game with SB sound effects)
  needs a second IRQ line: a board revision, or a hardware modification on
  PicoGUS 1.x boards.
- On one shared IRQ line the combined firmware is still useful when only one
  of the two drivers is loaded at a time, since it avoids switching firmware
  between network and sound use.

## How the two modes work today

| | SB mode (`play_adlib`) | NE2000 mode (`play_ne2000`) |
|---|---|---|
| Core 0 | ISA I/O polling loop, device register handlers | same |
| Core 1 main loop | OPL3 rendering into a 256-sample FIFO, DSP command processing, USB host, CD-ROM, MIDI out | WiFi requests from core 0 (send frame, status), reconnect check every ~4 s |
| Core 1 IRQs | 44.1 kHz audio sample IRQ (lowest priority), ISA DMA PIO IRQ and DSP timers (highest) | CYW43 background work (lowest priority), CYW43 host-wake GPIO IRQ |
| ISA resources | ports 220h, 388h, 330h, 250h (CD), 201h; one IRQ; one DMA channel | ports 300h–31Fh; one IRQ |

Core 0 must stay free of anything slow, since the ISA bus is held with
IOCHRDY while it runs a register handler. So in a combined firmware all the
WiFi work belongs on core 1, next to the audio.

## Resource budget

Static RAM is code copied to RAM, initialised data and zeroed data; heap is the
rest of main SRAM.

| Firmware | RP2040 static | RP2040 heap | RP2350 static | RP2350 heap |
|---|---|---|---|---|
| SB (dbopl3) | 167 KB | 89 KB | 162 KB | 349 KB |
| NE2000 | 59 KB | 197 KB | 57 KB | 455 KB |
| SB + NE2000 | 196 KB | 60 KB | 191 KB | 321 KB |

The CYW43 firmware (226 KB) stays in flash. The NE2000 allocates a 33 KB
buffer at WiFi start-up, which on RP2040 would leave about 26 KB for the
CD-ROM and USB code's allocations. The combined build is limited to RP2350.

| Resource | Use in SB + NE2000 | RP2350 has |
|---|---|---|
| PIO | pio0: ISA IOW (10 instructions), IOR (9), SB DMA (12) = 31/32. pio1: I2S (8) + CYW43 SPI (5–7) | 3 PIO blocks; pio2 unused |
| DMA channels | 2 (CYW43 SPI) | 16 |
| Timer alarms | default pool, PIC events pool, CYW43 | 8 |
| GPIO | ISA bus, I2S, MIDI as today; CYW43 uses the Pico 2 W's internal GPIO 23/24/25/29 | no conflicts |
| Flash | ~384 KB image | 4 MB |

## Scheduling on core 1

The CYW43 driver does its background work (moving frames over its SPI bus) in
an IRQ at `PICO_LOWEST_IRQ_PRIORITY`, the same priority as the audio sample
IRQ in SB mode. Equal priorities don't preempt each other, and one 1500-byte
frame takes roughly 300 µs on the 46 MHz bus. The audio IRQ writes one sample
per 22.7 µs period into the I2S FIFO; a delayed IRQ doesn't catch up, so every
missed period is a lost sample. In the combined firmware the audio IRQ runs at
`PICO_DEFAULT_IRQ_PRIORITY`, above the WiFi work and below the ISA DMA and DSP
timer IRQs. The Cortex-M33 has 16 priority levels (the RP2040's M0+ has 4), so
there is room to refine this further.

The OPL renderer, USB host and CD-ROM run in the core 1 main loop and get
preempted by WiFi work. The OPL FIFO holds 5.8 ms, so bursts of WiFi traffic
are absorbed. One thing to fix before relying on this:
`ne2000_initiate_send()` busy-waits `100 + length` µs after handing each frame
to the CYW43 (up to 1.6 ms), stalling the main loop. The frame has already
been copied to the chip by then, so the transmit-complete interrupt could be
raised straight away.

## The IRQ line

Both the Pico-based PicoGUS 1.x board and the chip-down PicoGUS 2.0 route one
GPIO (GPIO21, net `RIRQ`) through a buffer to one jumper block (IRQ 2, 3, 4, 5
or 7). There is one DRQ/DACK pair as well, which is fine: the NE2000 emulation
uses programmed I/O, not ISA DMA.

With both devices on that line:

- The ISA interrupt controller triggers on a rising edge, so a second device
  raising an already-high line produces no interrupt, and either device
  lowering the line on acknowledgement drops the other's request.
- The SB driver and the packet driver each install their own handler for the
  IRQ; neither chains to the other or checks the other device's status.

So the combined firmware only works with one driver using the interrupt at a
time. For real simultaneous use the NE2000 needs its own line, for example
IRQ 3 (if COM2 is unused) or 2/9 next to the SB on 5 or 7.

On the Pico footprint every GPIO is already wired. GPIO0–3 go to the GUS
PSRAM, which is unused outside GUS mode, so a modified 1.x board could drive
a second IRQ from one of them, for example GPIO3 (Pico pin 5, the PSRAM data
input), through a buffer like the existing IRQ output (the RP2350 isn't 5 V
tolerant) to a spare ISA IRQ pin. The PSRAM chip select (GPIO1) should then be
held high. A future board could expose a second IRQ jumper block properly.

## The experimental SB_NE2K firmware

```sh
sw/scripts/build_variants.sh -p rp2350 sb-ne2k     # -> binaries/pg-sb-ne2k-rp2350.uf2
# or, with the NE2000 on a dedicated IRQ output (hardware modification needed):
cmake -S sw -B build-sbne2k -DPICO_PLATFORM=rp2350 -DPROJECT_TYPE=SB_NE2K -DSB_NE2K_IRQ_PIN=3
```

It is the SB (dbopl3 OPL3) firmware with the NE2000 added, for a Pico 2 W:

- core 1 brings up WiFi before starting audio, then services WiFi requests
  from its main loop (`ne2000_core1_init()` / `ne2000_core1_task()`, shared
  with the NE2000-only firmware);
- the audio sample IRQ runs above the CYW43 background IRQ;
- the NE2000 shares the card's IRQ output, unless `SB_NE2K_IRQ_PIN` names a
  GPIO for a dedicated line;
- it reports itself to pgusinit as SB mode, so pgusinit shows SB settings.
  The WiFi and NE2000 commands (`/ne2kport`, `/wifissid`, `/wifipass`,
  `/wifistatus`) are accepted in every mode, but only listed in `/?` in NE2000
  mode.

## What a supported feature would need

1. A second IRQ line: board revision, or documented modification plus the
   `SB_NE2K_IRQ_PIN` option.
2. A mode of its own (e.g. `SB_NE2000_MODE`) so pgusinit can show both sets of
   settings and help, and a place in the firmware bundle: the multifw
   bootloader has six slots today, and NE2000 firmwares are separate files.
3. Non-blocking transmit completion in `ne2000_initiate_send()`.
4. Hardware measurements: core 1 idle time with OPL3 + SB DMA + CD audio +
   network traffic, and listening for dropped samples under WiFi load.
5. Locking between cores for the NE2000 state. Core 1 writes received frames
   and interrupt status while core 0 serves the host's register accesses, with
   no synchronisation; this is inherited from the NE2000-only firmware, where
   core 1 has much less else to do.
